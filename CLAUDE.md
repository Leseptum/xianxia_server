# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Xianxia is a 2D cultivation-themed multiplayer RPG. The backend is a SpacetimeDB module (C#); the only client currently in this repo is `web_client/`, a plain HTML/CSS/JS **proof-of-concept / test tool** for exercising the server (login, world map, Qi cultivation, movement) without needing the planned Godot client — see `web_client/README.md`. Don't assume a Godot client exists in this checkout; the top-level `README.md` describes the intended end-state stack, not what's implemented here.

## Repo layout

- `spacetimedb/` — the SpacetimeDB server module (C#, single file: `Lib.cs`). Builds to `wasi-wasm` (see `StdbModule.csproj`).
- `web_client/` — the TypeScript test client (Vite + the official `spacetimedb` SDK). Needs `npm install` and a build step now (see Commands below); the *built* `dist/` output is still static files servable by any plain HTTP server.
- `spacetime.json` / `spacetime.local.json` — CLI config (maincloud server + module path; local DB name `xianxia`).
- `scripts/publish.sh` — wraps `spacetime publish` and immediately re-sets the editor password afterwards (see below); prefer this over calling `spacetime publish` directly.

## Commands

### Server (spacetimedb/)

```bash
spacetime start                # run a local SpacetimeDB instance
scripts/publish.sh local       # build + publish the module locally, then set the editor password
scripts/publish.sh             # publish to maincloud (default), then set the editor password
spacetime logs xianxia -f                    # tail server logs
spacetime sql xianxia "SELECT * FROM player" # ad-hoc query (snake_case table/column names, see below)
```

`scripts/publish.sh [local|maincloud]` runs the equivalent `spacetime publish` (`--server local xianxia` or `xianxia --yes`) and then calls `set_editor_password` with the hash from the gitignored `editorpasswort` file at the repo root (sha256-hex of the chosen editor password — same format `web_client/editor.html` sends). `SetEditorPassword` no-ops if a password is already set (see server architecture below), so re-running the script against an already-initialized db is harmless — it exists purely so the password is never left unset after a fresh publish. If `editorpasswort` doesn't exist, the script publishes anyway and just warns instead of setting the password. Falling back to the raw commands (`spacetime publish --server local xianxia` / `spacetime publish xianxia --yes` + a manual `spacetime call ... set_editor_password <hash>`) still works identically if needed.

There is no formal test *framework* for the server (no xunit/nunit project — WASM reducers aren't easily unit-testable in isolation), but there are two black-box test scripts that drive a real local instance and assert on the results, both defaulting to `local` (never run against maincloud by accident):

```bash
scripts/smoketest.sh local      # register/qi/movement/collision/durchbruch/duplicate-name, one identity
node scripts/test_relogin.mjs   # the relogin regression test, needs two real Identities - see below
```

`scripts/smoketest.sh` isolates a fresh, run-specific `spacetime` CLI identity via a throwaway `XDG_CONFIG_HOME` (the CLI's default identity is otherwise stable *across* runs too, which would make `register` silently no-op on a second run) and asserts against `spacetime sql --format json` output with `jq`. `scripts/test_relogin.mjs` opens two real WebSocket connections directly via the `spacetimedb` SDK (from `web_client/node_modules`) — driving two distinct `Identity`s is the whole point (see `SenderPlayerId`/`PlayerSession` below) and isn't expressible through `spacetime call`, which only ever exposes one stable identity per invocation (or a brand-new throwaway one per call with `--anonymous`, never reusable across calls). Neither script touches the editor reducers (`EditorLogin`/`EditTile`/`SetEditorPassword`) — those need the gitignored `editorpasswort` secret.

### Web client (web_client/)

```bash
cd web_client && npm install          # once
npm run dev                           # Vite dev server (binds all interfaces, so LAN-IP access still works)
npm run build && npm run preview      # production build to dist/, then serve it locally to sanity-check
npm test                              # vitest: unit tests for the pure logic only (sha256, WorldGrid, deriveServerUri, clamp/toPlayerState)
```

`npm test` doesn't (and can't meaningfully) cover `app.ts`/`editor.ts`'s connection/DOM/render-loop code — that runs as an import-time side effect against a live `DbConnection` and real `index.html`/`editor.html` markup, not something jsdom + a mocked SDK can stand in for without a much heavier test harness. `app.ts`'s trailing `boot()` call is guarded behind `import.meta.env.MODE !== "test"` (Vitest sets `MODE` to `"test"` by default) purely so importing the module for its two pure exports (`clamp`, `toPlayerState`) doesn't also try to open a real WebSocket connection during a test run.

`dist/` after `npm run build` is plain static files — any HTTP server can host it, same as before.

Talks to `ws://<page-hostname>:3000` by default over plain HTTP pages (LAN dev), or `wss://db<page-hostname>` on HTTPS pages (reverse-proxied/tunneled) — both derived from the URL the page was loaded from, not hardcoded; see `src/config.ts` below. Override with `?server=...&db=...` query params (an `http(s)://` override is accepted too and normalized to `ws(s)://`).

Whenever `spacetimedb/Lib.cs`'s tables/reducers change, regenerate the client bindings (checked into git, not gitignored, so `npm install` alone is enough for anyone else to build):

```bash
spacetime generate --lang typescript --out-dir web_client/src/module_bindings
```

## Server architecture (`spacetimedb/Lib.cs`)

Everything lives in one `static partial class Module`. Nine tables: `WorldTile` (one row per map cell, 256×256), `WorldMeta` (singleton, generation status/seed), `Player` (public gameplay state: name, Qi/cultivation stats, position — no credentials), `Credential` (**not** `Public`: `PlayerId` → `PasswordHash`, kept out of the public SQL/subscription interface since it's the only login secret and there's no server-side salting), `LoginAttempt` (public, but carries no secret — just `PlayerId` + a `Success` bool so a client can observe its own `Login` outcome without a hash ever being readable back), `EditorSecret` (**not** `Public`, singleton: the map-editor password hash), `EditorSession` (public, no secret: `Identity` → `Authorized` bool, gates `EditTile`), `PlayerSession` (**not** `Public`: `Identity` → `PlayerId`, see `SenderPlayerId` below).

- **World generation** runs once, in the `Init` reducer (fires on first publish): Perlin noise (custom implementation at the bottom of the file, not a library) determines biome per tile via `WeltGenerieren`, gated by `WorldMeta.Generiert` so it never regenerates on republish — bump the seed/params and manually reset that flag (or the DB) if you need a fresh map.
- **`PlayerId` resolution / `SenderPlayerId(ctx)`**: every player-scoped reducer (`UpdatePosition`, `QiSammeln`, `Durchbruch`) resolves the acting `PlayerId` itself via the private `SenderPlayerId(ctx)` helper rather than accepting it as an argument — a client can only ever act on its own row this way. (Earlier revisions took `playerId` as a plain client-supplied argument on those three reducers, which let any connected client move, buff, or force a breakthrough on any *other* player by passing their id — fixed by deriving it server-side instead.) `SenderPlayerId` first looks up `PlayerSession.Identity.Find(ctx.Sender)` — populated by `Register` (binding your own new row) and by `Login` on a successful password check (binding *this* connection's `Identity` to the target account) — falling back to `(ulong)Math.Abs(ctx.Sender.GetHashCode())` if no session row exists yet. The `PlayerSession` lookup is what makes relogin from a *different* connection/`Identity` (new tab, cleared session, another device) actually work: without it, a successful `Login` only wrote a `LoginAttempt` row and displayed the right `Player` row client-side, while every subsequent action reducer kept resolving `PlayerId` from the *new*, never-registered `Identity`'s raw hash and silently no-op'd — a regression that shipped in the same change that introduced `Credential`/`LoginAttempt`, caught and fixed before ever being committed. `scripts/test_relogin.mjs` is a permanent regression test for exactly this scenario, since it needs two real `Identity`s (a real second WebSocket connection) to exercise — not expressible via `spacetime call`, see that script's header comment.
- **Password handling**: the client hashes the password (SHA256, `web_client/src/sha256.ts`) before ever sending it; the server does no additional salting. `Register` stores that hash in `Credential` (private table, see above). `Login` looks the player up by name, compares against `Credential`, and writes the pass/fail result to `LoginAttempt` for that `PlayerId` — it never sends the hash back to any client, and `Credential` can't be read via `spacetime sql`/the HTTP SQL endpoint at all (only from within reducers, via `ctx.Db.Credential`).
- **`Durchbruch` (breakthrough)** uses `new Random()` (not `ctx.Rng`) for the success roll — this violates the determinism rule reducers are otherwise supposed to follow ([[SpacetimeDB Critical Rules]] in `.windsurfrules`/`AGENTS.md`/`.cursor/rules/`); be aware if touching this reducer.
- **`UpdatePosition` enforces collision**: it looks up the target tile via `WorldTile.TileId.Find((uint)(ix + iy * WELT_BREITE))` — same formula `WeltGenerieren` uses to assign `TileId`, so no extra index is needed for an O(1) lookup — and silently drops the update (position stays unchanged) if the tile is `Wasser` or `Berg`. Water/mountain are also blocked client-side (`web_client/src/app.ts`) for immediate visual feedback, but the server check is what actually prevents a modified/malicious client from walking through them.
- **`EditTile`** is the map-editor reducer (`web_client/editor.html`): overwrites a tile's biome + all four resource fields by `(x, y)`. Gated by `EditorSession.Owner.Find(ctx.Sender)` having `Authorized = true` — no-ops otherwise, same as every other reducer here. `EditorSession` is populated by `EditorLogin(ctx, passwordHash)`, which checks the caller's hash against the single row in the private `EditorSecret` table and writes the pass/fail bool for that `ctx.Sender`. That secret is set exactly once via `SetEditorPassword` — invoked automatically right after publish by `scripts/publish.sh` (see Commands above), or manually via `spacetime call <db> set_editor_password <sha256-hex>`, **never** from the web client, so the actual editor password never touches `web_client/` source or git; it no-ops if already set, so it can't be overwritten later by an arbitrary caller. Bounds- and enum-range-checked, silently no-ops otherwise like every other reducer here.
- Field/column naming: C# struct fields are PascalCase (`PlayerId`, `PasswordHash`), but the wire format and SQL interface expose **snake_case** (`player_id`, `password_hash`) — any client, tool, or `spacetime sql` query must use snake_case regardless of the C# field name. (`password_hash` specifically lives on the private `Credential` table, so it's exempt from the "any `spacetime sql` query can read it" part — `spacetime sql` run server-side still can, browser/HTTP clients can't.)

General SpacetimeDB conventions (reducers are transactional and don't return data, must be deterministic, tables read via subscriptions/SQL not reducer return values, `ctx.Sender`/`ctx.Rng`/`ctx.Timestamp` for identity/randomness/time) are documented at length in `.windsurfrules`, `AGENTS.md` (identical to each other), and `.cursor/rules/*.mdc` (same reference material, split across `cli.mdc`/`concepts.mdc`/`csharp-server.mdc`) — none of these are project-specific notes.

## Web client architecture (`web_client/`)

TypeScript + Vite, using the official `spacetimedb` npm SDK (real WebSocket connection, subscriptions, and a locally-synced row cache) instead of hand-rolled HTTP polling. This is a deliberate departure from the original "no build step, no dependencies" POC design; the old hand-rolled `stdb_client.js` (raw `fetch()` calls, SQL built via string interpolation, and three near-duplicated polling/retry loops across `app.js`/`editor.js` to guess reducer success/failure) was error-prone enough that the user asked to switch to the vendor SDK, accepting npm/Vite as a new dependency in exchange. `dist/` (the `npm run build` output) is still plain static files, so deployment/hosting is unaffected — only local development changed.

- `src/module_bindings/` — **generated** by `spacetime generate --lang typescript` (see Commands above), checked into git like a lockfile. Never hand-edit; regenerate whenever `spacetimedb/Lib.cs`'s tables/reducers change. Exports `DbConnection`, `tables` (one entry per table, used both to `subscribe()` and as the `connection.db.<table>` accessor), and `reducers`. Table/reducer/column names are auto-**camelCased** from the wire's snake_case (`update_position` → `connection.reducers.updatePosition(...)`, `world_tile` → `connection.db.worldTile`, `player_id` → `row.playerId`); integer columns wider than 32 bits (`u64`/`i64`/...) decode as JS `bigint`, not `number` — e.g. `Player.playerId`/`qi`/`qiMaximum` are `bigint`, so `game.players` is keyed and compared with `bigint`, and HUD math needs `Number(...)` conversions.
- `src/connection.ts` — opens the connection via `DbConnection.builder().withUri(...).withDatabaseName(...).withToken(...).onConnect(...).onConnectError(...).build()`. Identity/token are still cached in **`sessionStorage`, not `localStorage`** — same reasoning as before: scoped per tab, so a second tab gets its own fresh identity for free, which is how you test two players at once (see `web_client/README.md`). `app.ts`'s "Logout" (`clearCachedIdentity()`) just clears this and reloads.
- `src/sha256.ts` — unchanged from the old `sha256.js` (just typed): a from-scratch pure-JS SHA-256, used instead of `crypto.subtle.digest` because Web Crypto only works in secure contexts and this client is also meant to be opened via a plain `http://<LAN-IP>`.
- `src/config.ts` — server/db picked via URL query params (`?server=...&db=...`); default server URI is derived from the page's own hostname/protocol. Over `http:` (localhost/LAN IP dev): `ws://<host>:3000`. Over `https:` (reverse-proxied/tunneled): `wss://db<host>` (e.g. page on `antalia.leseptum.de` → `wss://dbantalia.leseptum.de`), same tunnel convention as before, just `ws(s)` instead of `http(s)`. `app.ts`'s `boot()` still detects an `https:` page ending up with a `ws:` (non-`wss:`) server URI and surfaces that specific mixed-content case explicitly.
- `src/world.ts` — subscribes to `world_meta`+`world_tile` once at startup (the world is static outside the map editor) and, once the subscription is applied, packs `connection.db.worldTile.iter()` into a `Uint8Array` (`BYTES_PER_TILE` = 5: biome + kraeuter/spirit_stones/holz/erz per tile, indexed `x + y*width`), plus a pre-rendered offscreen `<canvas>` minimap for the full-map view. `getBiom(x, y)` only reads byte 0; `getTile()`/`setTile()` expose/mutate the full 5-byte tile and are what `editor.ts` uses — `setTile()` repaints just the affected minimap pixel.
- `src/app.ts` — state machine (`login` → `loading` → `game`). Subscribes to `player`+`login_attempt` right after connecting (before login/register are even usable) and registers `onInsert`/`onUpdate`/`onDelete` on `player` once, globally, to keep the `game.players` map live — **no more polling loop**: other players' moves arrive the moment the server pushes the row diff. `doRegister`/`doLogin` `await` the `register`/`login` reducer call directly; because the SDK resolves that promise only *after* applying the resulting row diffs to the local cache (same server message), the new `player`/`login_attempt` row is already readable from `connection.db...` the instant the `await` returns — no retry-polling needed to learn whether a name was taken or a password matched (both reducers still silently no-op/write a failed `LoginAttempt` rather than throwing, per the reducer-conventions note above, so success/failure is still read from table state, just synchronously instead of via a timed retry loop). `M` toggles between the camera-follow view and the full-map view. Movement is still **grid-based**: one integer tile per step, 4 directions only, throttled to `CONFIG.STEP_INTERVAL_MS` while a key is held; `isWalkable()` gates each step client-side before it's sent via `updatePosition`.
- `src/editor.ts` (+ `editor.html`) — standalone map editor, requires the shared editor password (see `EditTile`/`EditorSession` above). Subscribes to `editor_session` on connect, then reads this tab's own row via the SDK's unique-index accessor `connection.db.editorSession.Owner.find(connection.identity)` — replacing the old raw-SQL `WHERE owner = 0x<hex>` workaround entirely — to skip the password prompt if this tab already unlocked the editor earlier in the session. `attemptUnlock()` hashes the password, `await`s `editorLogin`, then re-checks that same lookup (populated synchronously for the same reason as `doLogin` above). Renders the map by scaling `worldGrid.minimapCanvas` onto a bigger `<canvas>` (`SCALE = 4` px/tile, `imageSmoothingEnabled = false` for crisp tile edges). A "brush" (biome + 4 resource values) is applied on click/drag via the `editTile` reducer; drag painting dedupes by tile.

Reducer/table names on the wire are still snake_case (matching the C# side, see the field/column naming note above) — the TypeScript bindings' camelCasing is a codegen convenience on top of that, not a change to the wire format.
