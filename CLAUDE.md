# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Xianxia is a 2D cultivation-themed multiplayer RPG. The backend is a SpacetimeDB module (C#). The **actual game client is `client/`** — Phaser 3 + TypeScript (Vite + the official `spacetimedb` SDK), isometric rendering; see "Game client architecture" below and `client/README.md`. New gameplay UI/features go there. The previously planned Godot client is **dropped** — there is no Godot project and none is planned.

`web_client/` is the older top-down TypeScript **proof-of-concept / test tool** (login, world map, Qi, movement, NPC attack) and hosts the **map editor** (`web_client/editor.html`) — keep it working, but it's no longer where the game itself evolves. Both clients talk to the same module and must keep working against it.

## Repo layout

- `spacetimedb/` — the SpacetimeDB server module (C#, single file: `Lib.cs`). Builds to `wasi-wasm` (see `StdbModule.csproj`).
- `client/` — the Phaser 3 game client (TypeScript, Vite, `spacetimedb` SDK). Own `package.json`/`node_modules`, independent of `web_client/`.
- `web_client/` — the TypeScript test client + map editor (Vite + the official `spacetimedb` SDK). Needs `npm install` and a build step now (see Commands below); the *built* `dist/` output is still static files servable by any plain HTTP server.
- `spacetime.json` / `spacetime.local.json` — CLI config (maincloud server + module path; local DB name `xianxia`).
- `scripts/publish.sh` — wraps `spacetime publish` and immediately re-sets the editor password afterwards (see below); prefer this over calling `spacetime publish` directly.
- `scripts/players.sh [local|maincloud]` — read-only `spacetime sql` helper listing all registered players (id/name/level/qi/position); defaults to `maincloud`.

## Commands

### Server (spacetimedb/)

```bash
spacetime start                # run a local SpacetimeDB instance
scripts/publish.sh local       # build + publish the module locally, then set the editor password
scripts/publish.sh             # publish to maincloud (default), then set the editor password
spacetime logs xianxia -f                    # tail server logs
spacetime sql xianxia "SELECT * FROM player" # ad-hoc query (snake_case table/column names, see below)
```

`scripts/publish.sh [local|maincloud]` runs the equivalent `spacetime publish` (`--server local xianxia` or `xianxia --yes`) and then calls `set_editor_password` with the hash from the gitignored `editorpasswort` file at the repo root (sha256-hex of the chosen editor password — same format `web_client/editor.html` sends). `SetEditorPassword` no-ops if a password is already set (see server architecture below), so re-running the script against an already-initialized db is harmless — it exists purely so the password is never left unset after a fresh publish. If `editorpasswort` doesn't exist, the script publishes anyway and just warns instead of setting the password. Falling back to the raw commands (`spacetime publish --server local xianxia` / `spacetime publish xianxia --yes` + a manual `spacetime call ... set_editor_password <hash>`) still works identically if needed.

There is no formal test *framework* for the server (no xunit/nunit project — WASM reducers aren't easily unit-testable in isolation), but there are two black-box test scripts that drive a real local instance and assert on the results, both defaulting to `local` (never run against maincloud by accident):

```bash
scripts/smoketest.sh local      # register/qi/movement/collision/durchbruch/duplicate-name/npc-tick, one identity
node scripts/test_relogin.mjs   # the relogin regression test, needs two real Identities - see below
```

`scripts/smoketest.sh` isolates a fresh, run-specific `spacetime` CLI identity via a throwaway `XDG_CONFIG_HOME` (the CLI's default identity is otherwise stable *across* runs too, which would make `register` silently no-op on a second run) and asserts against `spacetime sql --format json` output with `jq`. Its last section snapshots a couple `npc` rows, sleeps past one `NPC_TICK_INTERVALL`, and re-snapshots to assert at least one position changed — the only way to confirm the scheduled `NpcTick` reducer (see server architecture below) is actually firing, since that can't be verified by reading code alone. `scripts/test_relogin.mjs` opens two real WebSocket connections directly via the `spacetimedb` SDK (from `web_client/node_modules`) — driving two distinct `Identity`s is the whole point (see `SenderPlayerId`/`PlayerSession` below) and isn't expressible through `spacetime call`, which only ever exposes one stable identity per invocation (or a brand-new throwaway one per call with `--anonymous`, never reusable across calls). Neither script touches the editor reducers (`EditorLogin`/`EditTile`/`SetEditorPassword`) — those need the gitignored `editorpasswort` secret.

**Testing against an isolated throwaway server** (instead of the long-lived local dev db): `spacetime start --data-dir <tmp-dir> --listen-addr 127.0.0.1:3010 --non-interactive` in the background, then `spacetime publish -s http://127.0.0.1:3010 xianxia --yes` (explicit `-s`, so `spacetime.json`'s `maincloud` default can't kick in) and point a client at it with `?server=ws://127.0.0.1:3010`. `Init` generates map 1 on first publish (a few seconds). Since `SetEditorPassword` accepts the first caller, you can set a *test* editor password there (`spacetime call -s http://127.0.0.1:3010 -y xianxia set_editor_password <sha256-hex>` + `editor_login <same>` with the same CLI identity) and use `spieler_verschieben`/`edit_tile` from the CLI — e.g. to move a test player off the water spawn (see `Register` under Server architecture). Kill exactly the PIDs you started afterwards, never by name (the user's own `spacetime`/`vite` may be running in `screen`).

### Game client (client/)

```bash
cd client && npm install              # once
npm run dev                           # Vite dev server (host: true, LAN-IP access like web_client)
npm run build                         # tsc --noEmit + vite build -> dist/ (Phaser in its own chunk)
npm run preview                       # serve dist/ locally
npm test                              # vitest: pure logic only (iso, interpolation, movement, combat, emitter + the modules shared with web_client)
npm run typecheck
```

Same server-URI derivation and `?server=...&db=...` override as `web_client` (its `src/config.ts` is shared, see below). Unlike `web_client`, `npm run build` type-checks first.

### Web client (web_client/)

```bash
cd web_client && npm install          # once
npm run dev                           # Vite dev server (binds all interfaces, so LAN-IP access still works)
npm run build && npm run preview      # production build to dist/, then serve it locally to sanity-check
npm test                              # vitest: unit tests for the pure logic only (sha256, WorldGrid, deriveServerUri, clamp/toPlayerState)
```

`npm test` doesn't (and can't meaningfully) cover `app.ts`/`editor.ts`'s connection/DOM/render-loop code — that runs as an import-time side effect against a live `DbConnection` and real `index.html`/`editor.html` markup, not something jsdom + a mocked SDK can stand in for without a much heavier test harness. `app.ts`'s trailing `boot()` call is guarded behind `import.meta.env.MODE !== "test"` (Vitest sets `MODE` to `"test"` by default) purely so importing the module for its two pure exports (`clamp`, `toPlayerState`) doesn't also try to open a real WebSocket connection during a test run.

`dist/` after `npm run build` is plain static files — any HTTP server can host it, same as before.

Talks to `ws://<page-hostname>:3000` by default over plain HTTP pages (LAN dev), or `wss://db<page-hostname>` on HTTPS pages (reverse-proxied/tunneled) — both derived from the URL the page was loaded from, not hardcoded; see `src/config.ts` below. Override with `?server=...&db=...` query params (an `http(s)://` override is accepted too and normalized to `ws(s)://`).

Whenever `spacetimedb/Lib.cs`'s tables/reducers change, regenerate the bindings of **both** clients (checked into git, not gitignored, so `npm install` alone is enough for anyone else to build). Run from the repo root (`spacetime.json` supplies the module path); the two outputs are byte-identical, so `diff -r web_client/src/module_bindings client/src/module_bindings` is a quick staleness check:

```bash
spacetime generate --lang typescript --out-dir client/src/module_bindings
spacetime generate --lang typescript --out-dir web_client/src/module_bindings
```

## Server architecture (`spacetimedb/Lib.cs`)

Everything lives in one `static partial class Module`. Eleven tables: `WorldTile` (one row per map cell, 256×256, **per map** — see multi-map note below), `WorldMeta` (**one row per map**, not a singleton — generation status/seed/name/Kernparameter), `StandardMap` (public, no secret, singleton `Id=0`: which `MapId` new `Register` calls land on, see below), `Player` (public gameplay state: name, Qi/cultivation stats, position, `MapId` — no credentials), `Npc` (public: map-populating creatures that move/react on a tick, see below), `NpcTickTimer` (public, scheduled table driving `NpcTick` — see below; empty of any meaningful data, just the interval), `Credential` (**not** `Public`: `PlayerId` → `PasswordHash`, kept out of the public SQL/subscription interface since it's the only login secret and there's no server-side salting), `LoginAttempt` (public, but carries no secret — just `PlayerId` + a `Success` bool so a client can observe its own `Login` outcome without a hash ever being readable back), `EditorSecret` (**not** `Public`, singleton: the map-editor password hash), `EditorSession` (public, no secret: `Identity` → `Authorized` bool, gates `EditTile` and every other editor-only reducer), `PlayerSession` (**not** `Public`: `Identity` → `PlayerId`, see `SenderPlayerId` below).

- **Multiple maps run concurrently.** `WorldTile`/`Npc`/`Player` all carry a `MapId` (`uint`); `WorldMeta` has one row per map (`[PrimaryKey][AutoInc] MapId`, starts at 1 — 0 is the `AutoInc` "assign me one" placeholder, not a real map). Players on different maps never see each other — the play client (`app.ts`) subscribes to `player`/`npc`/`world_tile`/`world_meta` filtered to its own player's `MapId` once logged in (see web client section below). `WorldTile.TileId` is a **global** key across maps, not just `x + y*Breite`: `WorldTileId(mapId, x, y) = ((ulong)mapId << 32) | (uint)(x + y*WELT_BREITE)` — chosen over a multi-column `[SpacetimeDB.Index.BTree(Columns=[...])]` because this SDK's query-side syntax for a multi-column index isn't documented anywhere in this repo's rule files; the folded key keeps every tile lookup a plain, provably-correct single-column `.Find()`. `Npc.NpcId` is `[AutoInc]` (global across maps, not map-scoped) so a second/third map's `NpcsPlatzieren` run can't collide with an earlier map's IDs.
- **`StandardMap`** is a singleton pointer (`Id=0` → `MapId`), exactly the same pattern as `EditorSecret`: "one row, always `Id=0`". `Register` reads it to decide which map a brand-new player lands on (`p.MapId = ctx.Db.StandardMap.Id.Find(0)`) and refuses to register if it's unset (shouldn't happen post-`Init`). The reason it's a separate table instead of an `IstStandard bool` column on `WorldMeta`: "at most one row has this flag set" isn't expressible as a SpacetimeDB column constraint (`[Unique]` on a `bool` just means "at most one `true` row *and* at most one `false` row", which breaks the moment a second map exists).
- **World generation** happens via `WeltGenerieren(ctx, mapId, seed, wasserAnteil, skala)` + `NpcsPlatzieren(ctx, mapId)` — both now parameterized (previously read the `SEED`/`WASSER_ANTEIL`/`SCALE` constants directly). `Init` (fires once, on first publish, gated by `WorldMeta.Iter().Any()` rather than a single row's flag) calls them once with those constants to create map `MapId=1` ("Standardwelt") and points `StandardMap` at it. The editor-only `KarteErstellen(ctx, name, seed, wasserAnteil, skala)` reducer calls the same two functions to spin up additional maps on demand — it runs the full Perlin generation inline (all 65536 tiles), so it takes real wall-clock time (seconds, not milliseconds); the editor UI shows a busy state rather than assuming an instant result. `OKTAVEN`/`PERSISTENZ`/`LACUNARITY`/`LAND_SHARES` stay global constants, not per-map — only Seed/Wasseranteil/Skala (+ Name) are editor-configurable per map.
- **NPCs (`Npc` table) spawn statically** via `NpcsPlatzieren`: rolls a small per-biome spawn chance per tile (`NPC_SPAWN_CHANCE` — `Wasser`/`Berg` are 0 because they're unwalkable, same rule `IstBegehbar` enforces; `Schnee` is currently also 0, but that's just a tuning choice, not a walkability rule) and, on a hit, picks a `NpcKategorie` (`Tiere`/`Menschen`/`Fabelwesen`) via per-biome weights (`NPC_KATEGORIE_GEWICHTE`) and one of 3 concrete `NpcArt` species within that category, with per-species starting `Hp`/`HpMaximum` (`TIERE_HP`/`MENSCHEN_HP`/`FABELWESEN_HP`). ~200 NPCs result per 256×256 map (only Strand/Ebene/Wald currently spawn any). Uses `ctx.Rng` (not a local seeded `Random`, unlike `WeltGenerieren`/`BuildPerm`) since NPC placement has no reproducibility requirement across republishes. The map editor can also place/move/delete NPCs directly (`NpcErstellen`/`NpcVerschieben`/`NpcLoeschen`, editor-gated, see below). `Angreifen(ctx, npcId)` lets a player attack any adjacent (`NPC_ANGRIFF_REICHWEITE`, all 8 neighboring tiles), *same-map* (`n.MapId != p.MapId` is checked and rejected — a client could otherwise pass an arbitrary cross-map `npcId`) NPC — resolves the attacker via `SenderPlayerId(ctx)` like every other player-scoped reducer (see below), deals fixed `NPC_ANGRIFF_SCHADEN` damage, and deletes the `Npc` row outright at 0 HP: no respawn, no loot/reward, by design.
- **NPCs move and react via a scheduled tick** — `NpcTickTimer` (`ScheduleAt.Interval(NPC_TICK_INTERVALL)`, 3s, one row inserted once in `Init`) drives `NpcTick`, the module's **first scheduled-table reducer** (the `Scheduled`/`ScheduledAt` table-attribute pattern from `AGENTS.md`/`.cursor/rules/csharp-server.mdc`). `NpcTick` iterates every `WorldMeta` row and runs `NpcsBewegen(ctx, mapId)` per map independently (so a `KarteErstellen`-created map's NPCs join the ecosystem automatically, no extra wiring). Each species' reaction is a static, data-only `NpcVerhalten` profile keyed by `NpcArt` (`NPC_VERHALTEN[]`, indexed `0`-`8`) — perception radius, a `BeuteMaske`/`BedrohungMaske` bitmask over `NpcArt` (which species it hunts/flees, built via the `Maske(...)` helper), `FliehtVorSpielern`/`NaehertSichSpielern` for player-reactivity, and an idle `WanderChance` — so behavior is entirely data (e.g. the Hase→Wolf→Tiger chain, Räuber preying on Wanderer/Einsiedler), not per-species code branches; `NpcsBewegen` is the one generic sense→decide→move loop shared by all 9 species (`NaechstesZiel` finds the nearest in-range threat/prey — a player counts too when the profile says so — `SchrittRichtung` takes one greedy step toward/away from it, `ZufaelligerSchritt` handles idle wandering). Movement reuses `IstBegehbar(ctx, mapId, x, y)`, factored out of `UpdatePosition`'s old inline water/mountain check so both now share the single source of truth for walkability. An NPC that doesn't act a given tick (nothing sensed, failed wander roll) never calls `.Update(...)` — the deliberate throttle against write/subscription-diff volume across ~200 NPCs/map. **NPC-vs-NPC combat/eating is explicitly out of scope** — this is movement-only reaction; killing an NPC is still only possible via player `Angreifen`. Since predators and prey move at identical speed and react every tick (not gated by `WanderChance`, only idle wandering is), a chase never actually closes distance — expected given there's no kill mechanic yet, not a bug.
- **`PlayerId` resolution / `SenderPlayerId(ctx)`**: every player-scoped reducer (`UpdatePosition`, `QiSammeln`, `Durchbruch`, `Angreifen`) resolves the acting `PlayerId` itself via the private `SenderPlayerId(ctx)` helper rather than accepting it as an argument — a client can only ever act on its own row this way. (Earlier revisions took `playerId` as a plain client-supplied argument on those three reducers, which let any connected client move, buff, or force a breakthrough on any *other* player by passing their id — fixed by deriving it server-side instead.) `SenderPlayerId` first looks up `PlayerSession.Identity.Find(ctx.Sender)` — populated by `Register` (binding your own new row) and by `Login` on a successful password check (binding *this* connection's `Identity` to the target account) — falling back to `(ulong)Math.Abs(ctx.Sender.GetHashCode())` if no session row exists yet. The `PlayerSession` lookup is what makes relogin from a *different* connection/`Identity` (new tab, cleared session, another device) actually work: without it, a successful `Login` only wrote a `LoginAttempt` row and displayed the right `Player` row client-side, while every subsequent action reducer kept resolving `PlayerId` from the *new*, never-registered `Identity`'s raw hash and silently no-op'd — a regression that shipped in the same change that introduced `Credential`/`LoginAttempt`, caught and fixed before ever being committed. `scripts/test_relogin.mjs` is a permanent regression test for exactly this scenario, since it needs two real `Identity`s (a real second WebSocket connection) to exercise — not expressible via `spacetime call`, see that script's header comment.
- **`SpielerVerschieben(ctx, playerId, x, y)`/`SpielerLoeschen(ctx, playerId)`** (editor-only, map-editor "Spieler" tool) are a **deliberate, documented exception** to the "never take a client-supplied `playerId`" rule above: authorization comes from the separate `EditorSession.Authorized` channel, not from the target player's own identity — the same pattern `EditTile` already uses to let an authorized editor mutate arbitrary `WorldTile` rows. This is not a regression of the original impersonation bug (that bug was ordinary *gameplay* reducers accepting a client-supplied `playerId` with **no** separate authorization at all). `SpielerVerschieben` does **not** run `UpdatePosition`'s water/mountain collision check (an editor override, not gameplay movement). `SpielerLoeschen` also removes the matching `Credential`/`PlayerSession` rows so the account is fully gone, not a login-less husk.
- **Password handling**: the client hashes the password (SHA256, `web_client/src/sha256.ts`) before ever sending it; the server does no additional salting. `Register` stores that hash in `Credential` (private table, see above). `Login` looks the player up by name, compares against `Credential`, and writes the pass/fail result to `LoginAttempt` for that `PlayerId` — it never sends the hash back to any client, and `Credential` can't be read via `spacetime sql`/the HTTP SQL endpoint at all (only from within reducers, via `ctx.Db.Credential`).
- **`Durchbruch` (breakthrough)** uses `new Random()` (not `ctx.Rng`) for the success roll — this violates the determinism rule reducers are otherwise supposed to follow ([[SpacetimeDB Critical Rules]] in `.windsurfrules`/`AGENTS.md`/`.cursor/rules/`); be aware if touching this reducer.
- **`UpdatePosition` enforces collision** via `IstBegehbar(ctx, mapId, x, y)` (own player's `MapId`, never a client-supplied one) — looks up the target tile by `WorldTile.TileId.Find(WorldTileId(...))` and treats it as walkable if the tile doesn't exist yet or its `BiomTyp` isn't `Wasser`/`Berg`; silently drops the update (position stays unchanged) otherwise. `IstBegehbar` is the single walkability source of truth shared with NPC movement (see NPC tick above) — don't reintroduce a second inline copy of this check. Water/mountain are also blocked client-side (`web_client/src/app.ts`, `client/src/logic/movement.ts`) for immediate visual feedback, but the server check is what actually prevents a modified/malicious client from walking through them. Note that `UpdatePosition` does **not** check step distance/adjacency — it accepts any walkable target, so a modified client can teleport; both clients only ever send single-tile steps.
- **`Register` spawns every new player at a hardcoded `(128, 128)`**, which is `Wasser` for `SEED = 42` — and so are all of its neighbors, so a freshly registered player can't move at all until moved via the editor (`SpielerVerschieben`). Known, pre-existing, unfixed; it's a server change, so propose a fix (e.g. nearest walkable tile from the map center, or a per-map spawn point) rather than working around it in a client.
- **`EditTile`** is the map-editor's terrain-brush reducer (`web_client/editor.html`): overwrites a tile's biome + all four resource fields by `(mapId, x, y)` — takes `mapId` explicitly, unlike the player-facing reducers, since an editor session isn't tied to one map. Gated by the shared `EditorAuthorized(ctx)` helper (factored out of the inline check that used to live only in `EditTile`, now reused by `KarteErstellen`/`KarteAlsStandardSetzen`/`NpcErstellen`/`NpcVerschieben`/`NpcLoeschen`/`SpielerVerschieben`/`SpielerLoeschen` too) — no-ops otherwise, same as every other reducer here. `EditorSession` is populated by `EditorLogin(ctx, passwordHash)`, which checks the caller's hash against the single row in the private `EditorSecret` table and writes the pass/fail bool for that `ctx.Sender`. That secret is set exactly once via `SetEditorPassword` — invoked automatically right after publish by `scripts/publish.sh` (see Commands above), or manually via `spacetime call <db> set_editor_password <sha256-hex>`, **never** from the web client, so the actual editor password never touches `web_client/` source or git; it no-ops if already set, so it can't be overwritten later by an arbitrary caller. Bounds- and enum-range-checked, silently no-ops otherwise like every other reducer here.
- Field/column naming: C# struct fields are PascalCase (`PlayerId`, `PasswordHash`), but the wire format and SQL interface expose **snake_case** (`player_id`, `password_hash`) — any client, tool, or `spacetime sql` query must use snake_case regardless of the C# field name. (`password_hash` specifically lives on the private `Credential` table, so it's exempt from the "any `spacetime sql` query can read it" part — `spacetime sql` run server-side still can, browser/HTTP clients can't.)
- **Breaking schema changes and `spacetime publish`**: this codebase has already gone through breaking `Lib.cs` schema changes (adding `Npc`, adding multi-map `MapId`/`StandardMap`/reshaping `WorldMeta`) — SpacetimeDB has no documented migration path for a new required column on an already-published table; the only known fix for the resulting "Schema conflict" is a **data-destructive** republish (`spacetime publish <db> --delete-data=always --yes`, or `spacetime delete <db>` first). A wholly *new* table (e.g. `NpcTickTimer`) is, by contrast, an additive/non-breaking change and publishes fine without `--delete-data` — but if the new table also needs one-time setup that only happens inside the `Init` reducer (which no-ops once `WorldMeta` already has rows), that setup still won't run against an existing db without a data-destructive republish to let `Init` fire fresh. Fine to do freely against `local` (disposable test data, same convention `scripts/smoketest.sh` already assumes). **Never do this against `maincloud` without explicit, separate user confirmation at the time of deployment** — it wipes every real registered player. `scripts/publish.sh maincloud` deliberately does *not* pass `--delete-data=always` by default, precisely so a routine republish can't accidentally nuke production data; a schema-breaking maincloud deploy needs a one-off manual `spacetime publish xianxia --delete-data=always --yes` instead, only after that confirmation.

General SpacetimeDB conventions (reducers are transactional and don't return data, must be deterministic, tables read via subscriptions/SQL not reducer return values, `ctx.Sender`/`ctx.Rng`/`ctx.Timestamp` for identity/randomness/time) are documented at length in `.windsurfrules`, `AGENTS.md` (identical to each other), and `.cursor/rules/*.mdc` (same reference material, split across `cli.mdc`/`concepts.mdc`/`csharp-server.mdc`) — none of these are project-specific notes.

## Game client architecture (`client/`)

Phaser 3 (`phaser@^3.90`, imported as `import * as Phaser from "phaser"` — the ESM build has named exports, and npm's `latest` tag is Phaser 4, so keep the `^3` range) + the same `spacetimedb` SDK version as `web_client` (2.8.2, matching the CLI-2.7.0-generated bindings). Hard rule for this layer: **scenes never touch the SDK; `src/net/` never imports Phaser.**

- **Shared pure modules, copied from `web_client/src/`**: `sha256.ts`, `world.ts` (`WorldGrid` + `loadWorld`), `npc.ts`, `connection.ts` (sessionStorage identity) and the `sha256`/`world`/`config` tests are **byte-identical copies** — `diff web_client/src/<file> client/src/<file>` must stay empty; change both or neither (there's no shared package because `web_client/` was to remain untouched and a cross-import would pull in a second copy of the bindings/SDK). `config.ts` is an *adapted* copy: `deriveServerUri`/`SERVER_URI`/`DATABASE_NAME`/`STEP_INTERVAL_MS` unchanged, the top-down render constants replaced by iso/interpolation/zoom constants.
- **Scenes** (`src/scenes/`, keys in `keys.ts`): `Boot` (generates placeholder textures, creates `GameClient`, starts connecting) → `Login` (HTML form as a Phaser `DOMElement`, needs `dom.createContainer` in `main.ts`; `novalidate` so empty fields get the same message as `web_client` instead of a silently blocked native submit) → `World`, which `launch`es `Hud` in parallel (separate scene = separate, unzoomed camera). Network objects are handed over explicitly as scene data (`{ client }`, `{ client, session }`), no globals/registry. **Don't name scene members after `Phaser.Scene` properties** (`input`, `data`, `cameras`, `scale`, `time`, `events`, `add`, ...) — a `private input()` helper in `LoginScene` silently replaced the input plugin before it was caught.
- **`src/net/GameClient.ts`**: owns the `DbConnection`; login/register flow and messages are a 1:1 port of `web_client/src/app.ts` (`doRegister`/`doLogin`/`startGame`), including the two-stage subscription (`player` + `login_attempt` unfiltered from connect, `npc` + `world_meta`/`world_tile` filtered to the player's `mapId` in `enterWorld`). Row callbacks are registered once on connect and forwarded to the current `WorldSession` (which populates itself from the cache on creation, so nothing applied earlier is lost). It also forwards `world_tile` **updates** (inserts are the initial load), so map-editor terrain edits show up live and client-side collision uses the edited terrain — `web_client` doesn't do this.
- **`src/net/WorldSession.ts`**: map-scoped live state (`players`/`npcs` maps filtered by `mapId`, `worldGrid`) + every gameplay action (`step`, `collectQi`, `breakthrough`, `attack`), exposing changes through a small typed `Emitter` (`playerChanged`/`playerRemoved`/`npcChanged`/`npcRemoved`/`tileChanged`/`localMoved`/`notice`). `breakthrough()` reports success/failure by comparing `stufe`/`qi` before and after awaiting the reducer (the promise resolves after the row diffs are applied, same property `doRegister` relies on).
- **Own movement = client-side prediction + server reconciliation** (`PredictedPosition` in `src/logic/movement.ts`): a step is applied locally at once and sent via `UpdatePosition`; while own steps are in flight, incoming own-row updates are ignored (they're just those steps being confirmed — `UpdatePosition` has no sequence number, and a *rejected* move produces no row update at all), and once the last in-flight call settles the prediction is compared with the cached server row and corrected if different. With nothing in flight, own-row updates are adopted directly (editor `SpielerVerschieben`). Keys map to the same **grid** directions as `web_client` (W = y−1, D = x+1, ...); the iso projection makes them screen-diagonal (W = up-right, D = down-right, S = down-left, A = up-left).
- **Iso convention** (`src/logic/iso.ts`): tile `(x, y)`'s **center** is at `((x − y)·W/2, (x + y)·H/2)`, `W×H = 64×32`; integer server positions are tile centers, fractional (interpolated) ones project linearly. The ground is a real Phaser isometric `Tilemap` (`view/isoGround.ts`: own `MapData` with `orientation: ISOMETRIC`, one tile per biome). Phaser puts a tile's *top-left* at `((x − y)·W/2, (x + y)·H/2)`, hence the layer offset `(−W/2, −H/2)`. Its `cullCallback` is replaced by `forEachVisibleTile`, which visits only the visible diagonals analytically — Phaser's own `IsometricCullTiles` loops over all 65536 tiles every frame.
- **Interpolation** (`src/logic/interpolation.ts`, `InterpolatedPosition`): each new target is approached linearly from the *currently shown* position (retargeting mid-move never jumps), unchanged targets don't restart a move (Qi-only row updates), jumps beyond `SNAP_DISTANCE` snap. Remote players use `PLAYER_MOVE_MS` (= step interval → continuous walking), NPCs `NPC_MOVE_MS`. Phaser's camera-follow lerp is per frame, so on teleports and window resizes `WorldScene` re-centers the camera explicitly instead of letting it glide across the map.
- **Depth**: entities use their feet's world Y as depth (own player +0.5 on ties); ground at `-1e6`; name labels/HP bars at `1e6 + Y` so they're never hidden. Labels hide below `LABEL_MIN_ZOOM`.
- **Placeholder textures** (`view/textures.ts`): all generated at boot on canvases. Biome diamonds are drawn row-by-row with `fillRect` (no anti-aliasing) so neighbors overlap by 2px → no seams at fractional zoom; the tileset has 1px margin/2px spacing against texture bleeding. Figures are white and tinted per player/NPC category (colors as in `web_client`).
- **HUD** (`HudScene`): name/Stufe/Qi bar, Qi sammeln/Durchbruch/Angreifen (same enable rules as `web_client`), Karte (M)/Logout, transient notices. The `M` map overlay (`view/MapOverlay.ts`) reuses `WorldGrid.minimapCanvas`, rotated 45° inside a container scaled to half height, so it has the same diamond orientation as the world.
- **Background tabs**: Phaser pauses its loop while the page is hidden (SDK callbacks keep updating the session) — for side-by-side multiplayer testing use two windows, not two tabs (each still gets its own identity via sessionStorage). Same reason a headless test needs one browser per player.
- **Tests**: Vitest covers only Phaser-free modules (`src/logic/*`, `src/net/emitter.ts`, the shared copies) — don't import Phaser in tests. Scenes/`GameClient`/`WorldSession` need a live server + real browser; they were verified end-to-end against an isolated server (see "Testing against an isolated throwaway server" above) with headless Chromium, but no such browser test is checked in.

## Web client architecture (`web_client/`)

The older top-down test client and the map editor (see Project above).

TypeScript + Vite, using the official `spacetimedb` npm SDK (real WebSocket connection, subscriptions, and a locally-synced row cache) instead of hand-rolled HTTP polling. This is a deliberate departure from the original "no build step, no dependencies" POC design; the old hand-rolled `stdb_client.js` (raw `fetch()` calls, SQL built via string interpolation, and three near-duplicated polling/retry loops across `app.js`/`editor.js` to guess reducer success/failure) was error-prone enough that the user asked to switch to the vendor SDK, accepting npm/Vite as a new dependency in exchange. `dist/` (the `npm run build` output) is still plain static files, so deployment/hosting is unaffected — only local development changed.

- `src/module_bindings/` — **generated** by `spacetime generate --lang typescript` (see Commands above), checked into git like a lockfile. Never hand-edit; regenerate whenever `spacetimedb/Lib.cs`'s tables/reducers change. Exports `DbConnection`, `tables` (one entry per table, used both to `subscribe()` and as the `connection.db.<table>` accessor), and `reducers`. Table/reducer/column names are auto-**camelCased** from the wire's snake_case (`update_position` → `connection.reducers.updatePosition(...)`, `world_tile` → `connection.db.worldTile`, `player_id` → `row.playerId`); integer columns wider than 32 bits (`u64`/`i64`/...) decode as JS `bigint`, not `number` — e.g. `Player.playerId`/`qi`/`qiMaximum` and `Npc.npcId` are `bigint`, so `game.players`/`game.npcs` are keyed and compared with `bigint`, and HUD math needs `Number(...)` conversions.
- `src/connection.ts` — opens the connection via `DbConnection.builder().withUri(...).withDatabaseName(...).withToken(...).onConnect(...).onConnectError(...).build()`. Identity/token are still cached in **`sessionStorage`, not `localStorage`** — same reasoning as before: scoped per tab, so a second tab gets its own fresh identity for free, which is how you test two players at once (see `web_client/README.md`). `app.ts`'s "Logout" (`clearCachedIdentity()`) just clears this and reloads.
- `src/sha256.ts` — unchanged from the old `sha256.js` (just typed): a from-scratch pure-JS SHA-256, used instead of `crypto.subtle.digest` because Web Crypto only works in secure contexts and this client is also meant to be opened via a plain `http://<LAN-IP>`.
- `src/config.ts` — server/db picked via URL query params (`?server=...&db=...`); default server URI is derived from the page's own hostname/protocol. Over `http:` (localhost/LAN IP dev): `ws://<host>:3000`. Over `https:` (reverse-proxied/tunneled): `wss://db<host>` (e.g. page on `antalia.leseptum.de` → `wss://dbantalia.leseptum.de`), same tunnel convention as before, just `ws(s)` instead of `http(s)`. `app.ts`'s `boot()` still detects an `https:` page ending up with a `ws:` (non-`wss:`) server URI and surfaces that specific mixed-content case explicitly.
- `src/npc.ts` — shared NPC display constants (`NPC_ART_NAMES`, `NPC_KATEGORIE_NAMEN`, `NPC_KATEGORIE_FARBEN`, `NPC_KATEGORIE_ARTEN`), hoisted out of `app.ts` once `editor.ts` needed the same lookup tables for its NPC tool. Must be kept in sync by hand with `NpcArt`/`NpcKategorie` in `Lib.cs` — no shared source of truth.
- `src/world.ts` — `loadWorld(connection, mapId)` subscribes to `world_meta`+`world_tile` **filtered to one map** (`tables.worldMeta.where(row => row.mapId.eq(mapId))`, same for `world_tile` — SpacetimeDB subscriptions support a real server-side `WHERE` via the generated `.where()` query builder on every table accessor, confirmed safe/type-preserving for numeric predicates) and, once applied, packs the matching `world_tile` rows into a `Uint8Array` (`BYTES_PER_TILE` = 5: biome + kraeuter/spirit_stones/holz/erz per tile, indexed `x + y*width`), plus a pre-rendered offscreen `<canvas>` minimap. `getBiom(x, y)` only reads byte 0; `getTile()`/`setTile()` expose/mutate the full 5-byte tile and are what `editor.ts` uses — `setTile()` repaints just the affected minimap pixel. The `world_meta` row for a given map is looked up by key (`connection.db.worldMeta.MapId.find(mapId)`), not "the first/only row" — `world_meta` is multi-row now (one per map).
- `src/app.ts` — state machine (`login` → `loading` → `game`). Two-stage subscription: stage 1 (`boot()`, before login/register are usable) subscribes `player`+`login_attempt` **unfiltered** (name-uniqueness/`findPlayerByName` must see every player across every map); stage 2 (`subscribeToMap`, called from `startGame` once the logged-in player's own `mapId` is known) subscribes `npc` **filtered** to that map. `game.players` itself is still map-scoped despite the unfiltered `player` subscription — the `onInsert`/`onUpdate` handlers and `initGame`'s initial populate loop each check `row.mapId === game.localMapId`/`localPlayerRow.mapId` before adding a row, so a player registered on a different map never shows up locally even though its row *is* in the client-side cache. `game.npcs` stays server-filtered (no local map check needed there). Both maps live-sync via `onInsert`/`onUpdate`/`onDelete` — **no polling loop**: other players' moves (and NPC HP changes/deaths) arrive the moment the server pushes the row diff. `game.npcs` is rendered the same way as `game.players` (`drawNpcs()`, plus a dot loop in `drawFullMap()`), colored by `NPC_KATEGORIE_FARBEN[npc.kategorie]` and labeled via `NPC_ART_NAMES[npc.art]` (from `src/npc.ts`, see above). The "Angreifen" HUD button calls the `angreifen` reducer against whatever `nearestNpcInRange()` (client-side Chebyshev-distance-≤1 pre-check, UX only — the server's own range+same-map check in the reducer is the actual authority) finds; `updateHud()` enables/disables the button each frame based on that same check. `doRegister`/`doLogin` `await` the `register`/`login` reducer call directly; because the SDK resolves that promise only *after* applying the resulting row diffs to the local cache (same server message), the new `player`/`login_attempt` row is already readable from `connection.db...` the instant the `await` returns — no retry-polling needed to learn whether a name was taken or a password matched (both reducers still silently no-op/write a failed `LoginAttempt` rather than throwing, per the reducer-conventions note above, so success/failure is still read from table state, just synchronously instead of via a timed retry loop). `M` toggles between the camera-follow view and the full-map view. Movement is still **grid-based**: one integer tile per step, 4 directions only, throttled to `CONFIG.STEP_INTERVAL_MS` while a key is held; `isWalkable()` gates each step client-side before it's sent via `updatePosition`.
- `src/editor.ts` (+ `editor.html`) — standalone map editor, requires the shared editor password (see `EditTile`/`EditorSession` above). Subscribes to `editor_session` on connect, then reads this tab's own row via the SDK's unique-index accessor `connection.db.editorSession.Owner.find(connection.identity)` to skip the password prompt if this tab already unlocked the editor earlier in the session. `attemptUnlock()` hashes the password, `await`s `editorLogin`, then re-checks that same lookup (populated synchronously for the same reason as `doLogin` above). Once unlocked, `startEditor()` subscribes `world_meta` **unfiltered** (the one legitimate place in this codebase that wants every map's row at once, to populate the `#map-select` dropdown via `refreshMapList()`) and loads the first map. `selectMap(mapId)` — re-run on every `#map-select` change — re-subscribes `npc`+`player` **filtered** to that map (`loadWorld(connection, mapId)` for the terrain) and resizes/redraws the canvas; unlike `app.ts`, the editor doesn't bother keeping a separate map-scoped cache Map — it just reads `connection.db.npc.iter()`/`connection.db.player.iter()` filtered by `row.mapId === currentMapId` on every render, since a stale cross-map row lingering client-side after switching maps a few times is harmless (filtered out on read) and this isn't a 60fps game loop. Three tool tabs (`currentTool: "terrain" | "npc" | "player"`, `#tool-tabs` buttons) swap which panel is visible and which handler `handlePointerAt` dispatches to: **Terrain** (`paintTerrain`) is the original biome/resource brush via `editTile` (now takes an explicit `mapId` argument, since an editor session isn't tied to one map); **NPC** (`handleNpcPointer`) creates a new NPC via `npcErstellen` on an empty tile, or selects-then-drag-moves (`npcVerschieben`)/deletes (`npcLoeschen`) an existing one; **Spieler** (`handlePlayerPointer`) only selects-then-drag-moves (`spielerVerschieben`)/deletes (`spielerLoeschen`) an existing player dot — no create affordance, players only come from `Register`. Zoom is a mutable `scale` variable (mouse wheel or +/− buttons, clamped 1–16), replacing the old fixed `SCALE = 4` constant; canvas width/height and every screen-coordinate calculation derive from it. Hover (`updateHover`) shows biome name + all four resource values (`worldGrid.getTile`) plus NPC/player info when the hovered tile has one, regardless of which tool is active.

Reducer/table names on the wire are still snake_case (matching the C# side, see the field/column naming note above) — the TypeScript bindings' camelCasing is a codegen convenience on top of that, not a change to the wire format.
